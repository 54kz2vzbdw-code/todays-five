# Today's Five 1.7 — Bug hunt: sync and data

(The agent could not write this file itself; the text below is its final report, verbatim, saved by the orchestrator. Scripts: `model-probe.mjs`, `tz-probe.mjs`, `import-move.mjs` (Node, against the source tree's `model.js`); `tdz.mjs`, `browser.mjs`, `lifecycle.mjs` (Playwright on `?transport=local`). Each has a `.out` beside it.)

### A list with a "chosen days" repeat never syncs: the first paint dies in a temporal dead zone
- severity: blocker
- environment: every environment; fixture `longtime` (and any list holding a weekly repeat with 1–6 chosen days on a line in the first paint). Reproduced on desktop, light and dark.
- steps: 1. Open the app on a device whose list has a line with Repeat → Chosen days (the shipped `longtime` fixture has three). 2. Console: `ReferenceError: Cannot access 'DAY_NAMES' before initialization` at `app.js:752`. 3. The top bar says **SYNC OFF**. 4. Add a line. Nothing reaches the server; `tf/v3/list/<id>` stays `{ rev: 0, dirty: true }` for ever.
- evidence: `tdz.out`, `tdz-longtime-cold-start-desktop.png` (header reads "SYNC OFF"), `tdz-weekly-rule-cold-start-desktop.png`, `roll-midnight.out` (the same throw twice, on the harness's two loads). The control in `tdz.out` is decisive: a `fresh` list boots with `sync.current()` populated; give one of its lines `{kind:"weekly", days:[1,4]}` and reload → `sync` is `NOT CREATED`; set `days:[0..6]` (the branch that returns "Every day" without touching `DAY_NAMES`) and it boots clean again.
- why it matters: `const DAY_NAMES` is declared at `app.js:747`, below the top-level `boot()` call at `app.js:256`. `boot() → openList() → setView() → render() → renderToday() → updateRow() → ruleLabel()` reads it during the first paint, before the module body reaches line 747. The throw aborts `openList` at `setView(view, {force:true})` (`app.js:424`), so **everything after it never runs**: no `ref`, no `createSync`, no channel, no poll, no `flushOthers`, no `applyCarry`, no save-your-link sheet. The list looks normal apart from a small "Sync off", and every edit in that session is stranded on one device — the other device, the server and any later paste of the link never see it. This is the app's own documented hazard: `app.js:127` — "Everything below is reachable from boot() … declare it here, never further down, or a cold start straight into a link dies in a temporal dead zone."
- proposed fix: move `const DAY_NAMES` up beside `STATUS_LABEL` (~`app.js:129`). Then guard the class of bug: wrap the `boot()` call in a try/catch that still paints, and assert in the e2e suite that `window.__tf().cur` is non-null and no page error fired for the `longtime` fixture. A scan of module-level `const` declared after line 256 finds only `DAY_NAMES` in a first-paint path today, but nothing stops the next one.

### A device in a timezone ahead rolls the day over for everyone else, mid-morning
- severity: bug (near-blocker on a shared list: the vanished line survives only as History text)
- environment: model level, `TZ=Asia/Tokyo` + `TZ=America/Chicago`; two devices on one list
- steps: 1. A shared list is open on a laptop in Chicago and a phone in Tokyo (14 hours apart in September). 2. In Chicago, cross a line off at 08:00 on Saturday 5 September. 3. At 10:30 Chicago it is 00:30 Sunday in Tokyo; the Tokyo minute tick runs `rollover`. 4. Tokyo files the line under History `2026-09-05` and tombstones it, then pushes. 5. The Chicago laptop merges and the line disappears from the list at half past ten in the morning.
- evidence: `tz-probe.out` — "Chicago: 'crossed off at breakfast' is GONE FROM THE LIST (tombstoned by Tokyo)"; "Chicago: History under today (2026-09-05) = ['crossed off at breakfast']".
- why it matters: a line crossed off two hours ago is deleted mid-day, and the day the person is still living in already has a History page. Because a rollover tombstone is deliberately *bare* (`model.js:479`, DECISIONS.md line 176), the line is **not** in Recently deleted: the only trace is the History text, which must be retyped. A repeating line is instead reset to undone mid-morning, silently discarding the check-off. This argues against DECISIONS.md line 15 — "It is a pure function of the doc (`doneAt` earlier than today ⇒ move), so two devices doing it independently merge to the same result." True only while every device agrees what "today" is; `rollover(doc, today)` takes `today` from the device clock and `localDate` from the device zone, so a list rolls over at the *earliest midnight among its devices*.
- proposed fix: pin the day boundary to the document. Store the list's home zone (or UTC offset) on the doc at creation and have `rollover` compute both `today` and `localDate(doneAt)` in it, falling back to the device zone when absent — an additive key, so old clients pass it through (COMPATIBILITY.md §3). Failing that, refuse to roll a line whose `doneAt` is less than ~6 hours old.

### New keys: a stale device's unpushed edits are carried over only if the new link is *pasted*, not opened
- severity: bug (data loss on a plausible path)
- environment: desktop, fixture `fresh`, two pages on one context, local transport
- steps: 1. Device B holds the private link and makes an edit it has not pushed (`dirty: true`, `rev: 2`). 2. Device A does Share → New keys. 3. B is sent the new link and *opens* it (a click, or the address bar) rather than pasting it into Lists → "Paste a link". 4. B's unpushed line is gone from B and never reaches A.
- evidence: `rotate.out` — B's stored state before the rotate is `{"rev":2,"dirty":true}`; after B opens the new link, "B typed this before it heard about the rotate" is absent from B's rows and never appears in A's. `rotate-b-gone-desktop.png`, `rotate-b-new-link-desktop.png`.
- why it matters: `applyCarry()` (`app.js:592`) only fires when `meta.carry` is set, and `meta.carry` is only set by `switchTo(r, { paste: true })` (`app.js:1880-1886`). Every call site: `paste: true` comes from exactly two places — the Lists paste box (`panels.js:439`) and the welcome paste form (`app.js:1908`). Arriving by URL goes through `boot() → openList()` or `hashchange → switchTo(r)` (`app.js:366`) with no flag, so the carry never runs. Clicking the link someone sends you is the normal way to arrive.
- proposed fix: move the lineage check out of the paste path. On any `openList` of an edit link, if the registry holds a `redirect` to this id (or a `dead` id whose local copy is dirty and shares item ids with the doc that arrives), run `applyCarry` however the person got here.
- caveat, stated honestly: the harness's two "devices" are two pages of one profile and share `localStorage`, including `tf/v2/meta` and its redirect map. That makes the *registry* half of this scenario untrustworthy here (B's tab wrote a stale `meta` over A's, which is why B's old link did not redirect and B never showed "This link no longer works"). The carry finding itself is a code-path fact confirmed by the observed loss.

### Importing a JSON export silently renames the open list
- severity: bug
- environment: model level; path is Settings → Advanced → Export & import → "Merge into this list" (`panels.js:558-566`)
- steps: open a list named "Work"; import a JSON export of another list called "Holiday packing"; choose Merge into this list. The toast says "Merged: 1 new line". The list is now called "Holiday packing".
- evidence: `import-move.out` — `FAIL the list keeps its own name / the list is now named "Holiday packing" — it was "Work"`.
- why it matters: `merge()` resolves the name by `nameAt`, so whichever document was renamed most recently wins, and the imported file usually was. The person is told only about lines. The same merge folds in the other list's History days, saved themes and templates (also in that output) — defensible for a whole-document merge, but the message never says so.
- proposed fix: keep the open list's name on a merge-import (`merged.name = A.doc.name; merged.nameAt = A.doc.nameAt`), and widen the toast.
- copy line: `panels.js:565`, current `` `Merged: ${after - before} new line${after - before === 1 ? "" : "s"}` ``; new string: `` `Merged: ${newLines} new line${newLines === 1 ? "" : "s"}, ${newDays} day${newDays === 1 ? "" : "s"} of history. The list keeps its name.` ``

### Undoing "Move to another list" drops the line into Unsorted
- severity: bug
- environment: model level; path is a line's menu → Move to another list… → the toast's Undo (`panels.js:774-780`)
- steps: a line sits in "Errands"; move it to Home; press Undo in the "Moved to Home" toast inside 10 s. The line is back in this list — in Unsorted, not Errands.
- evidence: `import-move.out` — "the line came back as id n2, section "" (it was "s1")".
- why it matters: the undo is offered as a way back and half-works — text, note, repeat rule and Not-today return all survive (`model-probe.out`) — but the line's place does not, so someone with six sections has to hunt for it and re-file it. `moveItem` always writes `sectionId: ""` (`model.js:700`), right for a move and wrong for its reverse.
- proposed fix: give `moveItem` an optional target `sectionId` (default `""`) and have the toast's undo pass the section the line left, which `moveTo` already has in scope as `it.sectionId`.

### `purgeTombstones` is not a fixed point: an orphaned repeat survives one extra open
- severity: papercut
- environment: model level (`model.js:286-306`)
- steps: hold a doc with a 31-day-old tombstone whose line still has a repeat rule; call `purgeTombstones` twice.
- evidence: `model-probe.out` — `FAIL a second purge is a no-op (same object back)`, plus "rule for the line whose tombstone was just purged: KEPT this pass".
- why it matters: the orphan test at `model.js:300` reads `doc.items[id]` — the *input* map — not the map being built, so a rule whose item is purged in this very pass still looks attached. The document changes on two consecutive opens instead of one: one extra push, one extra revision, for nothing. Harmless, but it makes "purge is idempotent" false, and the rest of the model leans hard on idempotence.
- proposed fix: build `out.items` first and test against it (`!(out.items && out.items[id])`), or run the collections in two passes.

### The Markdown export prints every Today line twice
- severity: papercut
- environment: model level (`model.js:731-752`), from Settings → Export & import → Markdown
- steps: export a list as Markdown where the starred lines also live in sections.
- evidence: `model-probe.out`, the "--- markdown export ---" block: "post the form" and "water the plants" appear once under `## Today` and again under `## Errands`.
- why it matters: the export reads as a document, and a document listing the same task twice looks like a mistake rather than a view; anyone printing or pasting it dedupes by hand.
- proposed fix: mark the Today lines in place instead of repeating them — keep the `★` in the section listing and drop `## Today`, or keep `## Today` and list only the unstarred lines under each section.

### The losing side of a simultaneous edit disappears without a word
- severity: proposal
- environment: desktop, fixture `fresh`, two pages, `tf/test/lag = 8000` on B
- steps: B (lagging 8 s) edits a line to "B's version of the line"; A edits the same line to "A's version" a moment later; both settle on A's text and B's words are nowhere in the document.
- evidence: `conflicts.out` ("A now shows / B now shows" both "A's version of the line"; "the loser's text is nowhere in the document — both texts present: false"), `conflict-edit-both-desktop.png`; model-level twin in `model-probe.out`.
- why it matters: last-writer-wins is the right rule here and the merge is correct — but the person who typed the losing words watches their line change under them with no explanation and no way back: not in Recently deleted, not in History, not in their local undo stack. On a shared list this is the only place the app throws work away silently.
- proposed fix: when a pull replaces the text of a line this device edited in the last minute or two, toast once — "Someone else's edit replaced yours" with an Undo that restores the pre-merge snapshot the engine already holds (`me.doc`). No new storage; one message and one button.

---

**What this lens found the app does well.** The document model is the strongest part of the app. `merge` really is a lattice join: over 400 random triples built from every collection — items, sections, themes, rules, returns, templates, history, plus unknown future keys on the document *and* on records — it is commutative, associative, idempotent and absorbing, with no case where a line was invented or a collection dropped. `rollover` is genuinely clock-independent: run on two devices whose wall clocks differ by 30 years it produces byte-identical records, merging the two changes nothing, and a re-run moves nothing; a device asleep three days files work under the day it was finished and writes nothing for the days it missed. Dates are handled with real care — `addDays`, `weekdayOf` and `isDue` anchor at noon, so the skipped hour on 2026-03-08 and the repeated hour on 2026-11-01 both land on the right calendar day and a streak counts through both nights; monthly rules clamp correctly to 30-day months and to February. A tab left open eight simulated hours polls exactly on the four-minute live cadence, makes **zero** server reads across six hours hidden, re-pulls on wake, rolls the day over across the spring-forward night without a reload, and costs 15 reads and 0 writes in an idle hour. `import(export(doc))` is exactly `normalize(doc)` — rules, returns, templates, saved themes, history, remembering tombstones and unknown future collections all survive, the list secret never appears in the file, a second import adds nothing, and both refusal messages are readable. Delete-everywhere is clean end to end: the other device is told "This link no longer works" while keeping its own copy on screen, the ten-second Undo brings the list back under the same link, and the other device recovers on its next load. The rate-limited server behaves exactly as designed: "Server busy — retrying in a few minutes", a five-minute hold with no retry storm, a line typed during the hold kept and pushed when the hold lifts, status back to "Synced".

**What I could not check, and why.** No real server: everything ran on the same-origin `local` transport, so nothing here speaks to Supabase's RPC semantics, its realtime channel, presence over a real socket, the 96 KB row cap (413), the storage-full path (507), or a genuinely flaky network — only to the engine's reaction to those statuses. The harness's "two devices" are two pages of one profile and share `localStorage`, which is fine for the transport and merge-on-write but unreliable for anything touching the device registry (the redirect map after New keys, "Remove from this device", the `carry` lineage) — hence the caveat on the New-keys finding. The `longtime` rollover convergence check passed but is vacuous, because the blocker means neither page was syncing at all; both were reading the same localStorage. I did not exercise iOS Safari's reload-on-switch path (`switchTo` under `IOS && !STANDALONE`), the v2→v3 plaintext migration (`migrateLegacy`, `settleMigrations`), the view-link/403 path beyond the shipped tests, or a real laptop suspend as opposed to a dispatched `visibilitychange`. Budget ran out before I could re-run delete-vs-edit and simultaneous-finish through the browser UI; both are proved at the model level in `model-probe.out` (a later edit resurrects a deleted line, an earlier one loses for good, a line whose section was deleted falls back to Unsorted and shows in exactly one place, two devices crossing off the same last line agree on one record).
