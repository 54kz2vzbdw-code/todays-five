### BUG-1 · Cross-tab: the `removed` mark is per-tab memory, so the removing tab keeps re-removing a list another tab has taken back — and both tabs then boot into "Whose list is this?"

- **Severity**: bug.
- **Where**: `app.js:75–100` (`saveDevice`: `removed = new Set([...(stored.removed || []), ...(meta.removed || [])].filter(id => !unremoved.has(id)))`), `app.js:463–466` (`registerList` clears the mark only from *this* tab's `meta.removed`), no `storage` event listener anywhere (`grep -n '"storage"\|onstorage' app.js panels.js sync.js` → nothing). Commit `67cdf4b`.
- **What was claimed**: PLAN.md:1690–1696 / DECISIONS.md "Removal had to be named, not just done": "A second tab could hand back a list this one had just removed … Removal is named now, the way Delete everywhere names a dead id, and `registerList` clears the mark because pasting the link again is the way back."
- **What I measured, with what**: `tools/a-crosstab-v2.mjs` on 8891 (log `a-crosstab-v2.log`). Tab A makes X; tab B opens in the same context and shows X. S2 — A removes X: storage `lists:[] removed:[X] current:null`. S3 — B pastes X's link as a real navigation (`?transport=local&tab=b#/l/X`), answers the Whose dialog "mine": storage `lists:[X] removed:[]` (the paste works, as the suite says). S4 — A makes one ordinary settings change (the sun/moon flip, which calls `saveDevice`): storage is back to `lists:[] removed:[X] current:null` — A's in-memory `meta.removed=[X]` re-removed the list B had just taken back. S5 — B makes the same flip: storage `lists:[] removed:[X] current:X`; B's own registry now lacks the list that is on B's screen: `B's Lists panel rows: 0`. S6 — B reloads: `listId:null, whoseOpen:true` (the Whose dialog for X again). S7 — A reloads: `listId:null, whoseOpen:true` — the tab that removed X is asked whose list X is, because B's save wrote `current:X` back and the local copy is still there (BUG-3). No page errors in either tab. The first run (`a-crosstab.log`) used a hash-only `goto` (a same-document navigation, no reload) and shows the other order: B's own save drops X from the registry while X is open, without A doing anything after the removal.
- **What the instrument cannot see**: a real second device (a different origin per device, so the fight cannot happen there — this is strictly two tabs of one browser profile); the phone viewport; the iPhone shell (which reads `tf/v2/meta` and would follow whichever tab wrote last).

- **Proposed repair** (one concern): a tab must not carry `removed` in memory across another tab's write. ### BUG-2 · Cross-build: a 1.11 tab left open across the deploy undoes a 1.12 removal on its next save, and the 1.12 tab gets the list back on reload

- **Severity**: bug (window: a tab or installed app left open across the deploy; §6 says that is a supported state).
- **Where**: `0e03143:app.js` `saveDevice` (no `removed` in its union; writes its whole in-memory `meta` back), against `67f35a5:app.js:75–100`.
- **What was claimed**: COMPATIBILITY.md §6 "An open page keeps its own code; a reload is the last resort" (by design), and PLAN.md "A user with a saved list opens 1.12 and sees exactly one new thing". The prompt asked that the cross-build case be reasoned from source; it was modelled instead.
- **What I measured, with what**: two ports cannot share an origin, so `tools/serve.js` served a scratch root with `old/` (= `git archive 0e03143`) and `new/` (= `git archive 67f35a5`) on 8895 — one origin, one `localStorage`, two builds — `tools/a2-crossbuild.mjs` (log `a2-crossbuild.log`). X1: the 1.11 tab (`version:"1.11"`) opens the list the 1.12 tab made. X2: 1.12 removes X: `lists:[] removed:[X]`. X3: 1.11 makes one settings change: storage `lists:[X] removed:[]` — its union put X back and it wrote back the stale `removed:[]` it loaded at boot (the key is carried through as an unknown key, so it is not dropped, it is overwritten with an old value). X4: 1.12 flips: `lists:[] removed:[X]`. X5: 1.11 flips: `lists:[X] removed:[]` — ping-pong. X6: 1.11 reloads and opens X. X7: **the 1.12 tab reloads and opens X** — the removal is gone, nobody pressed Undo.
- **Does §6's mismatch reload make it moot?** No. The reload fires only when a lazily loaded module asked for with the page's own build cannot be served; the worker keeps the previous build's cache for exactly that (§6, "The previous build's cache is kept for exactly that"), so a 1.11 tab opening Settings after the deploy gets `panels.js?v=151` from `tf-v1.11-b151` and never reloads. The 1.11 tab runs until the person navigates.
- **What the instrument cannot see**: the service worker itself (the local transport does not register it — `app.js:2386` registers only outside `?transport=local`), so the "kept cache serves the old panels.js" step is reasoning from §6, not a measurement; a real 1.11 page on Pages.
- **Evidence**: `review/raw/cleanup/a2-crossbuild.log`, `tools/a2-crossbuild.mjs`.
- **Proposed repair**: the same as BUG-1's — a stored `removed` that wins over memory would not fix a 1.11 writer (it does not know the key), so for the cross-build window the honest fix is the one COMPATIBILITY §5 already uses for `dead`: the 1.11 build's `saveDevice` unions `dead`, so an id in `dead` survives an old tab. Anything a new build wants an old tab to respect has to be a key the old build already merges — which `removed` is not. Say so in §6/§8 ("a removal made while a 1.11 tab is open comes back when that tab saves"), or accept it as the deploy window and write it down. Test: the same two-path model in the suite is cheap (serve two archived builds under one root).
